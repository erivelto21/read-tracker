## Context

The tracker API is a greenfield Golang/Gin service. The codebase currently contains only a stub `main.go`. This design covers the first real feature: `POST /v1/titles`, which introduces the full layered architecture (`domain → repository → usecase → handler`) and establishes patterns that all future endpoints will follow.

Stack: Go 1.25, Gin v1.12, go-playground/validator v10, mongo-driver v2.

## Goals / Non-Goals

**Goals:**
- Implement `POST /v1/titles` with type-conditional field validation
- Enforce title name uniqueness via usecase check + MongoDB unique index
- Establish the standard JSON response envelope for all future endpoints
- Wire the full Gin server with MongoDB in `cmd/api/main.go`

**Non-Goals:**
- Authentication / authorization (public endpoint for now)
- Pagination or listing endpoints
- Updating or deleting titles
- OpenAPI/Swagger spec generation

## Decisions

### 1. Separate Request DTO from Domain Struct

`handler.CreateTitleRequest` (with `json` + `validate` tags) maps to `domain.Title` (plain struct, no external dependencies) before calling the usecase. This keeps the domain free of HTTP/validation concerns, consistent with AGENTS.md.

**Alternative considered**: single struct for both — rejected because it leaks HTTP tags into the domain layer.

### 2. Type-Conditional Validation via `required_if` Tags

Conditional field presence (chapter required for book/manga/manhua/novel, page required for book, link required for manga/manhua/novel) is expressed using `go-playground/validator` `required_if` tags on the request DTO.

Pointer types (`*int`, `*string`) are used for optional fields so the validator can distinguish "not provided" from "zero value".

**Alternative considered**: manual validation in usecase — rejected because AGENTS.md mandates validating in the handler before calling the usecase.

### 3. Uniqueness: Usecase Check + MongoDB Unique Index

The usecase calls `repo.FindByName` before `repo.Save`. If found, it returns `domain.ErrAlreadyExists` → handler responds `409 Conflict`. The MongoDB unique index on `name` acts as a race-condition safety net.

**Alternative considered**: rely solely on the MongoDB unique index and parse the duplicate-key error — rejected because it leaks storage-layer errors into business logic and produces less clean error messages.

### 4. Standard JSON Response Envelope

All responses are wrapped in a consistent envelope:

```
Success  → { "data": { ... } }
Error    → { "error": { "code": "...", "message": "...", "details": [...] } }
```

`details` is only present on `400 Validation Error`. Internal errors never expose details to clients.

**Shared response helpers** live in `handler/response.go` so all future handlers reuse them.

### 5. No Internal ID Exposed on Response

MongoDB generates `_id` internally. The domain struct holds it for repository use only (bson tag `"_id,omitempty"`), and it is never serialised to JSON.

A separate `ExternalID` field (UUID v4, generated by the usecase before saving) is returned as `"id"` in all responses. Future lookup endpoints (e.g., `GET /v1/titles/:id`) will use this public identifier, keeping MongoDB internals fully hidden from clients.

## Risks / Trade-offs

- **`required_if` tag verbosity**: with 4 types requiring chapter, the tag becomes long. Acceptable tradeoff for declarative, testable validation without custom code.
  → Mitigation: keep tags on one logical line per field; add a comment in code.

- **Race condition on uniqueness check**: between `FindByName` and `Save` a duplicate could slip through. The unique index catches it and returns a mapped `409`.
  → Mitigation: repository maps mongo duplicate-key error (`E11000`) to `domain.ErrAlreadyExists`.

- **Greenfield wiring complexity**: `main.go` goes from a stub to full DI wiring in one step.
  → Mitigation: keep `main.go` focused on wiring only; no business logic there.
